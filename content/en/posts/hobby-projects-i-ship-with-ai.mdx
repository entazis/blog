I had a tidy idea: run a 7-day vibe-coding challenge. Each day, one side project built with AI, with a short write-up on how it started, what stuck, what broke, and what I took away.

While I was wiring up <SiteLink href="/en/posts/openclaw-telegram-to-deployment">OpenClaw</SiteLink> for an experiment, the setup started doing something louder than my plan. It was pushing a new app most mornings with very little “vibing” on my side, almost on autopilot. I wrote about the cron side of that in <SiteLink href="/en/posts/ai-ships-new-app-every-morning">another post</SiteLink>. By the time I got serious about drafting day one, the challenge framing felt redundant.

The interesting part was not the streak. It was that over the last few months, AI tools had slipped into how I build almost everything without me treating it as a special mode.

I still say “vibe-coding” sometimes because it is the word people reach for. If I am being precise, I call it AI-assisted work. There is still a human doing the thinking, saying no, debugging, ripping out half-baked output, and steering until something is actually useful. What changed is that the gap between “I have an idea” and “I have something running” got a lot smaller.

## Starting got cheap

I stopped letting small ideas rot in the notes app. They did not die because they were impossible. They died because starting used to mean a whole weekend: pick a stack, scaffold the repo, fight the layout, wire basic UI, and only then touch the interesting bit.

Now a lot of those ideas turn into a working prototype in one evening.

My site, [entazis.dev](https://entazis.dev), is a good example of the churn. The first pass came from [Bolt.new](https://bolt.new). The prompt asked for rich UI and motion, so the generator overshot, which was fair. I kept shaping it in [Cursor](https://cursor.com).

Later I flipped the order: spec first. I committed an overview, stack choice, features, implementation notes, even agent rules, and refined that text with [Claude](https://claude.ai), [ChatGPT](https://chatgpt.com), and [Perplexity](https://www.perplexity.ai) before any serious code generation. Only after that did I let an agent build in steps.

Then I tried [Lovable](https://lovable.dev) against the same spec. In a few minutes it produced a version that looked better than what I had been polishing by hand, so I merged that direction into my main branch and continued from there.

The same loop covered a wedding site when the date was getting close, and this blog. For both I wrote the spec first, used Lovable where I wanted a strong layout, then moved into Cursor to make it real. The wedding site got an RSVP form backed by Google Sheets and enough polish for guests. I did not treat it like a long-term product. For the blog I cared more about stack: Lovable’s plans looked great but stay on React and Vite with client rendering, which is weaker for SEO. I wanted Next.js with static generation, so I kept Cursor’s implementation and borrowed Lovable’s visual direction.

That loop repeats: think it through, write the spec, get a first version, then treat it like any other codebase. The model did not remove the work. It made the first chunk stupidly fast.

## Tools I actually open

One concrete case is [Flowmodoro](https://flow.entazis.dev), which is really just a timer. I built it because nothing else matched how I want to work. I wrote requirements, generated a first version in Lovable, then iterated in Cursor: sounds, themes, layout fixes, small UX tweaks. I have written about the idea behind it in <SiteLink href="/en/posts/from-pomodoro-to-flowmodoro">Flowmodoro: From Pomodoro to Momentum</SiteLink>.

I use it daily on hobby work. There is something satisfying about shipping a tool for yourself and nudging it whenever something annoys you.

## Learning while building

This might be the biggest shift. AI speeds up building, but for me it speeds up learning even more.

When I wanted basic observability, I started playing with Prometheus and Grafana without much prior setup experience. Instead of reading docs for hours in isolation, I asked an agent what to measure, what to change in the apps, what a sane layout looks like on a small personal server, and where the usual footguns are. Then I implemented alongside the answers and adjusted when reality disagreed.

I end up in two different postures. Sometimes I already know the shape of the solution and I want velocity. I can judge output quickly and my job is to keep the train on the tracks. When I am learning something new, I slow down: I watch the steps, ask why, and treat the agent like a tutor that can also type. That second mode has probably taught me more in the last year than a pile of passive tutorials.

## Not everything has to be useful

I also made a simple [Snake game](https://snake.entazis.dev/) because I felt like it. I generated variants in Cursor and Lovable, picked the one that looked nicer, then fixed responsiveness, added swipe on mobile, and played with browser automation. At one point I installed the Chrome DevTools MCP server and had the coding agent open the browser, read console errors, and patch its own mistakes. That felt genuinely odd in a good way, like watching a workflow from a few years in the future.

## Old ideas resurfacing

Some of this is plain fun, and some of it drags old projects back onto the table.

When I was a teenager I was deep into Hungarian hip-hop: lyrics, beats, recording, the whole amateur arc. University crowded it out.

Around 2017 I wondered whether I could train a small network to write rap lyrics for me. I scraped Hungarian lyrics, uploaded a dataset to AWS, grabbed an open-source text generation repo, and let it train for a day or two. The output was nonsense with occasional almost-words. Tiny model, no real pretraining, weak hardware, small data, nothing like what you get from a modern general model. I was still excited, in a “this direction might go somewhere” way.

Lately, with current tools, I keep thinking about revisiting that project, maybe with fine-tuning, maybe with long-context prompting, maybe just as a toy. It is still on the list. If someone told me they genuinely wanted to hear AI-generated Hungarian rap, it would jump a few slots.

## Less about code, more about curiosity

The more I use these tools, the less I think “vibe-coding” is really about code. It is about shrinking the distance between curiosity and something you can poke.

What if I had my own timer? What if my personal site had real metrics? What if I made a wedding website? What if I made a small game? What if I retried that lyrics model?

Those questions used to stall in my head. Now they often become experiments. Some are useful, some are silly, some turn into daily tools, plenty stay half-finished, but far more of them leave the idea stage than before.

I do not wait for the perfect weekend anymore. I start, get feedback fast enough to stay interested, and adjust. The part I enjoy is not that “the AI codes for me.” It is that building feels light again.

How does this land for you? Has AI changed how you spin up side projects, or how you pick up new tech while you build?
